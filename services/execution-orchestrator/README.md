# Execution Orchestrator v1

Оркестратор — доверенная граница между preview-планом Intent Compiler и
capability-модулями. В первой версии он исполняет только
`documents.query.search`: выполняет быстрый поиск, создаёт immutable snapshot и
обновляет серверный `TaskContext` идентификатором коллекции.

Планы не принимаются из HTTP как JSON. Compiler сохраняет объект плана в
ограниченном хранилище на 15 минут, а `POST /v1/plan/execute` принимает только
`plan_id`. Получение одноразовое, поэтому повторный запрос не повторяет действие.

Перед выполнением оркестратор заново проверяет UUID, состояние `ready`,
уникальность и порядок шагов, список capabilities, risk и approval-флаги.
Для `storage.materialize.plan-copy` оркестратор создаёт R1 preview с назначением,
именами, количеством и общим размером файлов, затем останавливается с
`awaiting_approval`. UI отвечает отдельным запросом. Одноразовый секретный grant
создаётся и потребляется только внутри ядра — наружу выходит лишь ID approval.
Отказ отменяет materialize-план без записи, подтверждение повторно проверяет
источники и выполняет rollback частично созданных файлов при любой ошибке.

Audit содержит только ID, состояния, коды ошибок и количество результатов. Текст
запроса, пути и snippets в журнал не записываются.

R1 endpoint доступен только через Unix socket с `SO_PEERCRED`; IPv4 loopback
является R0-only fallback. Peer credentials защищают от других пользователей, но
ещё не отличают панель от вредоносного процесса того же UID — для этого позже
понадобится дополнительная session-bound привязка клиента.
