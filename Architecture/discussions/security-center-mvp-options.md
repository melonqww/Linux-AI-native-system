# Дискуссия: границы Security Center MVP

**Итог:** выбран небольшой first-party модуль с детерминированной защитой и
третьим Security Campaign в существующей лаборатории.

Документ сохраняет варианты, рассмотренные до ADR-026 и ADR-027. Он не является
API и не обещает ещё не реализованные функции.

## Требования

- Правдоподобная архитектура защитного модуля для портфолио.
- Компактный последний модуль без попытки повторить коммерческий antivirus.
- Возможность позднее добавить карантин без всемогущего процесса.
- Внешняя воспроизводимая проверка без настоящего malware.

## Вариант 1 — один привилегированный сервис

Один background-процесс сканирует файлы, обновляет правила, хранит findings,
управляет карантином и меняет систему.

Плюс — простая коммуникация и меньше кода. Недостаток — совпадение всех границ
доверия: ошибка parser или detector получает полномочия updater и quarantine.
Постоянный root также противоречит текущему user-space core.

Вариант отклонён из-за слишком большого blast radius.

## Вариант 2 — обычный сторонний plugin

Независимый plugin сам запрашивает необходимые permissions. Это удобно для
расширяемости, но неподходяще для владельца привилегированных действий. Manifest
является недоверенной декларацией и не выдаёт право менять процессы или систему.

Вариант отклонён для coordinator. В будущем сторонними могут быть ограниченные
detector adapters, возвращающие только observations.

## Вариант 3 — отдельный Security Lab runner

Новая лаборатория получает собственные Virtual Host, supervisor и отчёты.
Изоляция предметной области привлекательна, но дублирование AI Scenario Lab
создаёт две версии containment и раздувает проект.

Вариант отклонён на MVP. `labs/security-lab` остаётся namespace документации и
fixtures, а Security Campaign расширяет существующий runner.

## Вариант 4 — выбранный

`security.center` является first-party capability-доменом. Foundation работает
on-demand и сначала публикует только status. Каждая новая функция получает
отдельный контракт и trusted policy. Будущие опасные роли разделяются между
scanner, updater, quarantine worker и минимальным privileged broker.

Проверка выполняется снаружи:

- обычные tests проверяют contracts, Registry и worker lifecycle;
- Security Campaign проверяет adversarial behavior и физические эффекты;
- Ubuntu VM подтверждает реальные Linux permissions и IPC.

Вариант требует явных контрактов, но позволяет наращивать только нужные
портфолио-MVP части. Неиспользуемые detector, updater и AI не создаются заранее.

## Решение об AI

Локальная модель для классификации угроз отклонена из MVP: inference добавляет
задержку и память, вредоносный файл является недоверенным prompt-контекстом, а
вероятностный ответ не подходит для hard verdict.

Необязательное объяснение findings может появиться позднее, но не получит права
изменять severity, policy или систему.

## Что может изменить решение

Отдельный Security Lab runner станет оправдан, если security fixtures или
supervision перестанут помещаться в существующую лабораторию. Постоянный
privileged daemon обсуждается только для доказанной real-time функции с
определёнными deployment, rollback и Linux threat model.

Принятые решения:

- [`ADR-026`](../decisions/ADR-026-security-center-foundation.md);
- [`ADR-027`](../decisions/ADR-027-security-campaign.md);
- [`ADR-028`](../decisions/ADR-028-security-file-scan-boundary.md) — trusted
  `resource_id + relative_path` и fail-closed сигнатурный scan для `0.2.0`.
