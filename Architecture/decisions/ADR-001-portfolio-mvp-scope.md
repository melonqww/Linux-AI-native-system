# ADR-001: Портфолио-MVP вместо универсального дистрибутива

**Статус:** принято 2026-08-17

**Проверка состояния 2026-09-16:** функциональный объём этого исходного MVP
реализован и существенно превышен. ADR сохраняется как историческое решение о
минимальной границе, а актуальная матрица Beta 0.1 находится в
[`AI-native-Linux-v0.1-концепция.md`](../AI-native-Linux-v0.1-концепция.md).
Формальный выпуск `0.1` всё ещё требует итогового Ubuntu smoke/release-gate:
наличие кода и unit-тестов не заменяет демонстрацию на целевой GNOME-системе.

## Контекст

Проект создаётся прежде всего как портфолио. Поэтому ценность первой версии — не покрытие всех дистрибутивов и сценариев, а короткая, понятная и надёжная демонстрация архитектурной идеи.

## Решение

v0.1 — локальное приложение для одной среды: Ubuntu Desktop 24.04 LTS с GNOME в VirtualBox. Первая демонстрация должна показать весь безопасный путь от запроса до результата:

```text
«Покажи состояние системы»
  → структурированное намерение
  → проверка policy layer
  → read-only system tool
  → audit event
  → понятный результат
```

В качестве первого runtime выбирается Python 3.12+. До запуска VM разрабатываются независимые от Ubuntu части: контракты, policy layer и unit-тесты. После установки VM добавляется Linux-адаптер для чтения системных метрик.

## Входит в MVP

- одно намерение `get_system_status`;
- фиксированный allowlist метрик;
- R0 policy без изменений системы;
- машинно-проверяемый audit event;
- CLI-демонстрация, а затем минимальная панель;
- тесты валидных и опасных/некорректных запросов.

## Не входит в MVP

- собственный Linux-дистрибутив;
- cloud fallback и API-ключи;
- unrestricted shell, `sudo` и root;
- полноценный поиск по файлам и индексатор;
- поддержка других DE и дистрибутивов.

## Последствия

Проект можно начать и тестировать без виртуальной машины. Ubuntu VM остаётся обязательной для финальной демонстрации реальной системной интеграции.

## Фактический результат

Все пункты исходного MVP закрыты:

- `get_system_status` вырос в `system.monitor.snapshot` с CPU, RAM/swap,
  температурой, батареей, дисками и bounded-списком процессов;
- allowlist и R0-risk назначаются доверенным Permission Gateway, а не моделью;
- Task Ledger и runtime фиксируют машинно-проверяемые состояния и безопасные
  пользовательские события;
- существуют CLI/API и нативная GNOME-панель;
- валидные, некорректные и опасные запросы покрыты unit/integration-тестами и AI
  Scenario Lab.

Сверх исходного scope реализованы локальная модель, поиск и PDF-индекс,
R1-копирование, Module Manager, установка приложений, Security Center и три
контура лабораторной проверки. Эти функции не следует задним числом объявлять
обязательными условиями первоначального MVP.
