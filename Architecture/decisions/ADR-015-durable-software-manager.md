# ADR-015: Долговечный модуль установки приложений

**Статус:** принято 2026-08-26

## Контекст

Панели AI-native Linux нужен пользовательский модуль, который устанавливает и
удаляет приложения, показывает фактический прогресс загрузки и не теряет
незавершённую задачу после закрытия панели, перезапуска процесса или перезагрузки
системы.

Нельзя связывать UI напрямую с произвольными shell-командами, передавать пароль в
`sudo` или считать текстовый вывод команды надёжным состоянием операции. Кроме
того, разные Linux package providers имеют разные контракты прогресса, отмены,
расположения установки и дополнительных компонентов.

На текущем этапе core нельзя полноценно проверить в целевой Ubuntu-среде. Поэтому
модуль должен разрабатываться и тестироваться автономно, без регистрации в
Capability Registry и без изменений существующего контура поиска и индексации
файлов.

## Решение

### 1. Единый capability-домен

Создаётся один крупный модуль `software.manager`. Он не дробится на отдельные
пользовательские модули установки, прогресса и удаления. Внутри домена код
разделяется на независимые компоненты:

- каталог приложений;
- публичные контракты и параметры установки;
- долговечное SQLite-хранилище задач;
- координатор жизненного цикла задачи;
- provider adapters;
- автономный CLI для проверки без панели и core.

Первая реализация находится в `modules/software-manager`. Она намеренно не имеет
`module.json`, поэтому текущий Capability Registry не обнаруживает и не запускает
её. Manifest, policy mapping и runtime routes добавляются отдельным решением после
проверки Linux-интеграции.

### 2. Snap-first backend

Первым provider adapter является `SnapdClient`. Он обращается к штатному Unix
socket `/run/snapd.socket` через версионированный REST API snapd и не использует
shell, `sudo` или передачу пароля.

Изменяющая операция запускается только после отдельного подтверждения. Для
запроса системной авторизации клиент разрешает штатное интерактивное
взаимодействие snapd с Polkit. Snapd возвращает asynchronous change ID, который
модуль сохраняет и использует для чтения состояния, прогресса и abort.

В v0.1 поддерживаются:

- подготовка установки;
- подготовка удаления;
- отдельное подтверждение подготовленной операции;
- получение текущего состояния и процента;
- остановка, продолжение и отмена установки;
- отмена удаления, пока backend разрешает abort;
- восстановление и сверка незавершённых задач после повторного запуска.

Pause не объявляется нативной паузой snapd. Модуль abort-ит текущий change и
сохраняет пользовательскую задачу в состоянии `paused`; resume создаёт новый
change для того же приложения. Snapd может повторно использовать локальные
данные, но точное продолжение с того же сетевого байта не гарантируется. Во время
фазы `installing` UI не предлагает pause.

### 3. Долговечные задачи

Пользовательская задача получает собственный `task_id`, а backend-операция —
отдельный `external_id`. Состояние сохраняется в SQLite с WAL и `synchronous=FULL`.

Основные состояния:

```text
awaiting_confirmation
  → running
  → paused → running
  → interrupted → running
  → completed | failed | canceled
```

После перезапуска менеджер не создаёт установку повторно. Он читает сохранённый
external change ID и сверяет его с snapd. Завершённый change закрывает задачу, а
прерванная установка становится доступной для явного resume.

Backend возвращает `progress_percent` только при наличии измеримого task progress.
Если корректный процент вычислить нельзя, значение остаётся `null`; UI обязан
показывать неопределённый прогресс и не придумывать число. Уже показанный процент
не движется назад в пределах одного change.

### 4. Встроенный каталог v0.1

В первую версию входит закрытый каталог из 20 точных Snap package IDs:

1. Steam (`steam`)
2. Discord (`discord`)
3. Spotify (`spotify`)
4. Telegram (`telegram-desktop`)
5. VLC (`vlc`)
6. Visual Studio Code (`code`)
7. Chromium (`chromium`)
8. Firefox (`firefox`)
9. OBS Studio (`obs-studio`)
10. Blender (`blender`)
11. Inkscape (`inkscape`)
12. GIMP (`gimp`)
13. Slack (`slack`)
14. Zoom (`zoom-client`)
15. Postman (`postman`)
16. PyCharm Community (`pycharm-community`)
17. IntelliJ IDEA Community (`intellij-idea-community`)
18. LibreOffice (`libreoffice`)
19. Thunderbird (`thunderbird`)
20. Bitwarden (`bitwarden`)

Произвольный package ID от модели или пользователя не передаётся backend. Все
имена проходят строгую проверку формата, а запросы строятся как HTTP/JSON без
командной строки. Наличие приложения в Snap Store означает доступность пакета,
но не обязательно официальную поддержку upstream-разработчиком; источник должен
быть виден пользователю перед будущим production-подключением.

### 5. Задел для следующих версий

Контракт `Application` уже объявляет:

- `supported_locales`;
- `supported_install_locations`;
- `install_options` для индивидуальных checkbox-компонентов.

Выбор сохраняется в задаче как `InstallPreferences`:

```json
{
  "locale": "system",
  "install_location": "default",
  "selected_options": []
}
```

В v0.1 разрешены только реально поддержанные значения `system`, `default` и
пустой набор опций. Русский язык, дополнительный диск или отдельные компоненты не
принимаются молча: менеджер возвращает стабильную ошибку до обращения к backend.
Позже конкретный adapter сможет расширить разрешённые значения без изменения
формата долговечной задачи.

APT и Flatpak добавляются как внутренние provider adapters того же
`software.manager`, а не как отдельные пользовательские модули. При этом нельзя
обещать custom location для provider, который сам её не поддерживает. PPA,
сторонние `.deb`, установка из произвольного URL и автоматическое добавление
репозиториев остаются вне v0.1.

## Проверка

Автономные тесты используют fake backend и проверяют:

- каталог и уникальность 20 package IDs;
- обязательное подтверждение;
- прогресс и запрет его обратного движения;
- pause, resume, cancel и remove;
- сохранение активной и приостановленной задачи после перезапуска менеджера;
- перевод прерванного change в resumable-состояние;
- сохранение будущих install preferences;
- отклонение неподдерживаемого языка, пути и checkbox-опции;
- защиту от option, path и shell injection;
- ограниченный разбор ответов snapd и сокрытие внутренних сообщений ошибки.

На момент принятия ADR целевой набор модуля содержит 13 успешных тестов и 4
security subtests; общий набор репозитория содержит 297 успешных тестов, 27
пропусков Linux-only проверок и 63 subtests. Реальная установка через snapd и
Polkit остаётся обязательным Ubuntu integration test перед подключением к core.

## Последствия

- Панель позднее получает единый контракт для каталога, прогресса и управления
  задачей независимо от package provider.
- Перезапуск UI или runtime не означает потерю операции или повторную установку.
- Snapd остаётся владельцем привилегированной транзакции и проверки пакета.
- Модуль не обещает неподдерживаемую настоящую паузу или произвольное место
  установки.
- Подключение к core потребует manifest, Permission Gateway policy, approval
  mapping, IPC routes и Linux integration tests.
- Установка и удаление остаются изменяющими действиями и не могут выполняться по
  одному лишь model output.

## Отложенные решения

- точные risk-классы download/install/remove/purge;
- формат preview размера, зависимостей, publisher и confinement;
- APT download/install boundary и поведение при критической фазе dpkg;
- Flatpak user/system installations;
- политика обновления встроенного каталога;
- поддерживаемые языки и опции каждого приложения;
- выбор дополнительных installation roots;
- интеграция карточки прогресса и управления задачей в GNOME-панель.
