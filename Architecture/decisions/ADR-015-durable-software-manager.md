# ADR-015: Долговечный модуль установки приложений

**Статус:** принято 2026-08-26, расширено 2026-08-29

## Контекст

Панели AI-native Linux нужен пользовательский модуль, который устанавливает и
удаляет приложения, показывает фактический прогресс загрузки и не теряет
незавершённую задачу после закрытия панели, перезапуска процесса или перезагрузки
системы.

Нельзя связывать UI напрямую с произвольными shell-командами, передавать пароль в
`sudo` или считать текстовый вывод команды надёжным состоянием операции. Кроме
того, разные Linux package providers имеют разные контракты прогресса, отмены,
расположения установки и дополнительных компонентов.

Core пока нельзя полноценно проверить в целевой Ubuntu-среде. Поэтому модуль
сначала разрабатывался автономно. После проверки контрактов в core подключается
только read-only вертикальный срез; файловый поиск, индексатор и PDF-модули при
этом не изменяются.

## Решение

### 1. Единый capability-домен

Создаётся один крупный модуль `software.manager`. Он не дробится на отдельные
пользовательские модули установки, прогресса и удаления. Внутри домена код
разделяется на независимые компоненты:

- каталог приложений;
- публичные контракты и параметры установки;
- долговечное SQLite-хранилище задач;
- координатор жизненного цикла задачи;
- provider adapters;
- автономный CLI для проверки без панели и core.

Первая реализация находится в `modules/software-manager`. Начиная с
интеграционного среза v0.2 она имеет `module.json`. Кроме read-capabilities
`software.catalog.read`, `software.tasks.read` и `software.backups.read`, второй
срез объявляет раздельные `software.install.prepare/commit`,
`software.remove.prepare/commit` и `software.tasks.control`.

### 2. Snap-first backend

Первым provider adapter является внутренний `providers.snapd.SnapdProvider`,
построенный поверх `SnapdClient`. Он обращается к штатному Unix
socket `/run/snapd.socket` через версионированный REST API snapd и не использует
shell, `sudo` или передачу пароля.

Изменяющая операция запускается только после отдельного подтверждения. Для
запроса системной авторизации клиент разрешает штатное интерактивное
взаимодействие snapd с Polkit. Snapd возвращает asynchronous change ID, который
модуль сохраняет и использует для чтения состояния, прогресса и abort.

В v0.1 поддерживаются:

- подготовка установки;
- подготовка удаления;
- отдельное подтверждение установки и два последовательных подтверждения
  удаления;
- получение текущего состояния и процента;
- остановка, продолжение и отмена установки;
- отмена удаления, пока backend разрешает abort;
- восстановление и сверка незавершённых задач после повторного запуска.

Pause не объявляется нативной паузой snapd. Модуль сохраняет намерение остановки,
abort-ит текущий change и сначала публикует `pausing`. Только подтверждённый
snapd-статус остановки переводит задачу в `paused`; resume создаёт новый change
для того же приложения. Snapd может повторно использовать локальные данные, но
точное продолжение с того же сетевого байта не гарантируется. Во время фазы
`installing` UI не предлагает pause и потеря сети не прерывает системную фазу.

### 3. Долговечные задачи

Пользовательская задача получает собственный `task_id`, а backend-операция —
отдельный `external_id`. Состояние сохраняется в SQLite с WAL и `synchronous=FULL`.

Основные состояния:

```text
awaiting_confirmation
  → awaiting_final_confirmation (только remove)
  → running
  → pausing → paused → running
  → pausing → waiting_for_network → running
  → retry_wait → running
  → recovering → running | retry_wait
  → canceling → canceled
  → completed | failed | canceled
```

После перезапуска менеджер не создаёт установку повторно. Он читает сохранённый
external change ID и сверяет его с snapd. Завершённый change закрывает задачу, а
прерванная безопасная фаза загрузки получает автоматический retry. Существующий
change всегда сверяется до создания следующего, поэтому обычный перезапуск не
создаёт дубликат установки.

Причина остановки хранится отдельно. `pause_reason=user` запрещает любое
автоматическое продолжение, в том числе после возвращения сети и перезапуска.
`pause_reason=offline` сохраняет последний достоверный процент и разрешает
автопродолжение. Пользователь может нажать pause даже в
`waiting_for_network`; тогда причина атомарно меняется на `user`.

`NetworkManagerMonitor` читает состояние через `nm-online` без тестового сетевого
запроса. `RecoveryWorker` вызывает reconciliation сразу при запуске будущего
user-session service и далее каждые две секунды. Временные ошибки используют
backoff 5, 15, 30, 60, 120 и до 300 секунд; после ограниченного числа попыток
нужна явная команда пользователя. Загрузка без реального прогресса пять минут
останавливается перед retry, но фаза `installing` watchdog-ом не прерывается.

Backend возвращает `progress_percent` только при наличии измеримого task progress.
Если корректный процент вычислить нельзя, значение остаётся `null`; UI обязан
показывать неопределённый прогресс и не придумывать число. Уже показанный процент
не движется назад в пределах одного change.

Для фазы `downloading` контракт также публикует `downloaded_bytes`,
`total_bytes`, сглаженную `download_speed_bps` и вычисленное `eta_seconds`.
Скорость и ETA появляются только после двух достоверных замеров и сохраняются в
SQLite. При завершении установки задача получает долговечное событие
`software_install_completed`. Linux-диспетчер отправляет его в стандартную
desktop-службу `org.freedesktop.Notifications` через `notify-send` и подтверждает
только после успешной доставки. Поэтому событие не теряется при перезапуске, а
панель не рисует собственную имитацию системного уведомления.

### 4. Встроенный каталог v0.1

В первую версию входит закрытый каталог из 20 точных Snap package IDs:

1. Steam (`steam`)
2. Discord (`discord`)
3. Spotify (`spotify`)
4. Telegram (`telegram-desktop`)
5. VLC (`vlc`)
6. Visual Studio Code (`code`)
7. Chromium (`chromium`)
8. Firefox (`firefox`)
9. OBS Studio (`obs-studio`)
10. Blender (`blender`)
11. Inkscape (`inkscape`)
12. GIMP (`gimp`)
13. Slack (`slack`)
14. Zoom (`zoom-client`)
15. Postman (`postman`)
16. PyCharm Community (`pycharm-community`)
17. IntelliJ IDEA Community (`intellij-idea-community`)
18. LibreOffice (`libreoffice`)
19. Thunderbird (`thunderbird`)
20. Bitwarden (`bitwarden`)

Произвольный package ID от модели или пользователя не передаётся backend. Все
имена проходят строгую проверку формата, а запросы строятся как HTTP/JSON без
командной строки. Наличие приложения в Snap Store означает доступность пакета,
но не обязательно официальную поддержку upstream-разработчиком; источник должен
быть виден пользователю перед будущим production-подключением.

### 5. Задел для следующих версий

Контракт `Application` уже объявляет:

- `supported_locales`;
- `supported_install_locations`;
- `install_options` для индивидуальных checkbox-компонентов.

Выбор сохраняется в задаче как `InstallPreferences`:

```json
{
  "locale": "system",
  "install_location": "default",
  "selected_options": []
}
```

В v0.2 разрешены только реально поддержанные значения `system`, `default` и две
post-install опции `pin_to_gnome`/`launch_after_install`. Русский язык,
дополнительный диск или неизвестные компоненты не
принимаются молча: менеджер возвращает стабильную ошибку до обращения к backend.
Позже конкретный adapter сможет расширить разрешённые значения без изменения
формата долговечной задачи.

APT и Flatpak добавляются как внутренние provider adapters того же
`software.manager`, а не как отдельные пользовательские модули. При этом нельзя
обещать custom location для provider, который сам её не поддерживает. PPA,
сторонние `.deb`, установка из произвольного URL и автоматическое добавление
репозиториев остаются вне v0.1.

### 6. Удаление, snapshot-бэкап и восстановление

`prepare_remove` по умолчанию сохраняет данные через штатный автоматический
snapshot snapd. Первое подтверждение лишь переводит задачу в
`awaiting_final_confirmation`; backend вызывается только отдельным
`confirm_removal`. Это позволяет панели показать финальный вопрос «Вы точно
хотите удалить?» непосредственно перед изменением системы.

Если пользователь явно отказывается от бэкапа, adapter передаёт snapd поле
`"purge": true`. Это поле входит в JSON-инструкцию snapd для remove и не
подменяется shell-командой.

`BackupStore` сохраняет сведения о snapshot set в той же SQLite-базе. Для
автоматического snapshot рассчитываются `remaining_seconds` и округлённые вверх
`remaining_days`. До чтения системной настройки используется стандартное
retention snapd 31 день, а результат помечается `expiry_estimated=true`; ручным
snapshot срок не назначается. После завершённого remove выполняется best-effort
синхронизация, а повторный sync после перезапуска восстанавливает сведения из
snapd.

Восстановление имеет долговечный фундамент:

```text
available → awaiting_restore_confirmation → restoring → available
```

Restore отправляется штатным `POST /v2/snapshots` с точным set ID и package ID,
сохраняет change ID и сверяется через progress API. Наличие установленного snap и
остановка приложения должны дополнительно проверяться при будущем подключении UI.

### 7. Фактическое состояние приложения в GNOME

Внутренний `ApplicationLifecycleManager` не считает успешный вызов launch
доказательством запуска. GNOME adapter использует `Shell.AppSystem.lookup_app`,
`Shell.App.get_state`, окна и PID; после 15-секундного тайм-аута неподтверждённый
запуск становится `launch_failed`.

Контракт UI намеренно ограничен:

- `running`/`running_in_background`: текст «Запущено» и только `close`;
- `launch_failed`: текст «Не удалось запустить» и только `retry`;
- установленное остановленное приложение: `launch`;
- действий `open` и `details` нет.

Close использует `Shell.App.request_quit()` и затем повторно проверяет состояние.
Принудительный kill не применяется. Закрепление меняет
`org.gnome.shell` → `favorite-apps` и перечитывает сохранённое значение.

### 8. Интеграция с runtime и GNOME-панелью

`software.manager` запускается Module Process Manager в отдельном background
процессе и получает собственную базу `software-manager.sqlite3`. Панель читает
единый snapshot каталога, задач и бэкапов через `/v1/software/snapshot`.
Endpoint доступен только через аутентифицированный Unix peer transport; loopback
HTTP его не публикует.

Настоящая GNOME-панель получает экран «Приложения» внутри настроек с разделами
«Каталог», «Библиотека» и «Бэкапы». Панель показывает данные, прогресс, скорость,
ETA, официальную страницу Snapcraft и локальное состояние недоступности. Второй
срез подключает install/remove/pause/resume/cancel. Установка показывает источник,
канал, язык и расположение перед подтверждением. Удаление показывает переключатель
бэкапа и отдельный финальный вопрос «Вы точно хотите удалить?». Снимок опрашивается
раз в две секунды, но дерево GNOME-акторов перестраивается только при изменении
данных; анимация применяется только при входе или открытии подтверждения.

Изменяющие endpoint проходят через системные Permission Gateway policies.
Prepare разрешён только secure transport со scope `software.manage`, а commit
установки/удаления дополнительно требует server-observed подтверждение. Worker
сверяет заявленный action и номер confirmation-stage с долговечной задачей, так
что UI не может подменить install на remove или пропустить второе подтверждение.
Loopback HTTP не публикует ни read snapshot, ни изменяющие endpoint.

Background reconciliation запускается не в `worker_start`, а внутренней операцией
`activate` после успешного создания единственного runtime Unix socket. Поэтому
второй экземпляр runtime, проигравший владение сокетом, не успевает изменить
состояние сохранённых задач.

GNOME adapter запуска и закрытия приложения остаётся внутри модуля и пока не
импортируется панелью: для него нужен отдельный JS↔runtime контракт. Файловый
поиск, индексатор и PDF-модули интеграция не меняет.

## Проверка

Автономные тесты используют fake backend и проверяют:

- каталог и уникальность 20 package IDs;
- обязательное подтверждение;
- двойное подтверждение remove и отдельный purge без бэкапа;
- прогресс и запрет его обратного движения;
- pause, resume, cancel и remove;
- сохранение активной и приостановленной задачи после перезапуска менеджера;
- перевод прерванного change в resumable-состояние;
- подтверждённую двухфазную pause и cancel без ложного финального состояния;
- ручную паузу при отсутствии сети и запрет её автоматического снятия;
- автоматическое продолжение после возвращения сети с сохранённым процентом;
- backoff, stalled-download watchdog и ограничение повторов;
- восстановление существующего snap change без дублирующей установки;
- миграцию SQLite schema v3 → v4;
- сохранение будущих install preferences;
- отклонение неподдерживаемого языка, пути и checkbox-опции;
- защиту от option, path и shell injection;
- ограниченный разбор ответов snapd и сокрытие внутренних сообщений ошибки;
- синхронизацию snapshots, долговечный countdown и подтверждённый restore;
- отсутствие ложного running до ответа GNOME, launch timeout, retry и
  подтверждаемое закрытие;
- точный контракт действий: без `open` у запущенного приложения и без `details`
  после ошибки запуска;
- GNOME favorites и обнаружение desktop ID из установленного Snap metadata.

После расширения ADR автономный набор `software-manager` содержит 39 успешных
тестов. Интеграционные тесты дополнительно проверяют manifest в Capability
Registry, изолированный background worker, 20 элементов snapshot, отложенную
активацию recovery, закрытие endpoint для loopback HTTP, runtime projection и
GNOME UI/runtime-client контракт, Permission Gateway и невозможность пропустить
двойное подтверждение удаления. Реальная установка через snapd, NetworkManager,
GNOME notifications, Unix peer credentials и Polkit остаётся обязательным Ubuntu
integration test.

## Последствия

- Панель получает каталог, прогресс, бэкапы и подтверждаемое управление задачей
  независимо от package provider.
- Перезапуск UI или runtime не означает потерю операции или повторную установку.
- Snapd остаётся владельцем привилегированной транзакции и проверки пакета.
- Модуль не обещает неподдерживаемую настоящую паузу или произвольное место
  установки.
- Изменяющее подключение защищено Permission Gateway policy и approval mapping;
  перед выпуском остаются Linux integration tests.
- Установка и удаление остаются изменяющими действиями и не могут выполняться по
  одному лишь model output.

## Отложенные решения

- уточнение risk-классов для будущих APT/Flatpak providers;
- формат preview размера, зависимостей, publisher и confinement;
- APT download/install boundary и поведение при критической фазе dpkg;
- Flatpak user/system installations;
- политика обновления встроенного каталога;
- поддерживаемые языки и опции каждого приложения;
- выбор дополнительных installation roots;
- подключение восстановления бэкапа и GNOME launch/close adapter к панели.
