# ADR-003: Минимальное системное ядро и подключаемые capability-модули

**Статус:** принято 2026-08-18

## Контекст

AI-native Linux должен поддерживать файловый поиск, документы, приложения,
браузер, голос, системную диагностику, модели и будущие интеграции. Если держать
все эти возможности внутри одного постоянно работающего процесса, система будет
потреблять лишние CPU и память, иметь слишком широкие права и становиться
хрупкой: сбой одного компонента затронет всё приложение.

Нужна модель, похожая по принципу на минимальное ядро и подключаемые подсистемы:
стабильная база управляет жизненным циклом, контрактами и безопасностью, а
конкретные функции появляются через модули. Это архитектурная аналогия, а не
изменение Linux kernel. AI-native core работает в user space поверх обычного
ядра Linux и не получает его привилегии автоматически.

## Решение

### 1. Минимальное обязательное ядро

Всегда доступный AI-native core содержит только системообразующие компоненты:

- Module Manager и Capability Registry;
- версионированные контракты сообщений и инструментов;
- маршрутизацию намерений и задач;
- policy engine и проверку scope;
- approval boundary;
- audit и состояние выполнения задачи;
- контроль жизненного цикла, здоровья и ресурсных лимитов модулей.

AI-провайдер не определяет доступные функции. Планировщик получает актуальный
список capabilities из Registry и строит план только из реально включённых
возможностей.

### 2. Capability-модули

Остальные функции реализуются крупными независимыми модулями, например:

- `storage.catalog` — хранилища, метаданные и коллекции;
- `documents.index` — извлечение текста и retrieval;
- `documents.pdf` — PDF, OCR, формулы и таблицы;
- `system.status` — CPU, RAM, диски, батарея и процессы;
- `systemd.diagnostics` — сервисы и журналы;
- `desktop.applications` — поиск и запуск приложений;
- `browser.navigation` — поиск сайтов и открытие URL;
- `voice` — распознавание и озвучивание;
- `model.local` и `model.cloud` — взаимозаменяемые model adapters;
- `developer.workspace` — проекты, Git, терминал и рабочие окружения.

Модуль добавляет системе capability, но не выдаёт себе доступ. Все обращения к
файлам, сети, приложениям и привилегированным операциям по-прежнему проходят
через Permission Gateway. Установка или включение модуля не означает
автоматического согласия на все запрашиваемые им права.

### 3. Manifest и совместимость

Каждый модуль публикует проверяемый manifest:

```json
{
  "module_id": "documents.pdf",
  "module_version": "1.0.0",
  "core_api": "1",
  "capabilities": ["extract_pdf_text", "search_pdf_content"],
  "dependencies": ["storage.catalog", "documents.index"],
  "optional_dependencies": ["documents.ocr"],
  "requested_permissions": ["read-document-content"],
  "lifecycle": "on-demand",
  "resource_class": "medium"
}
```

Module Manager проверяет уникальность ID, совместимость API, наличие
зависимостей и отсутствие циклов. Неизвестный, несовместимый или повреждённый
модуль не загружается молча и не публикует инструменты.

### 4. Жизненный цикл

Состояния модуля:

- `installed` — файлы модуля установлены;
- `enabled` — пользователь разрешил использование;
- `starting` — запускаются зависимости и выполняется health check;
- `running` — capabilities зарегистрированы и готовы;
- `idle` — модуль может быть выгружен;
- `disabled` — запуск запрещён, capabilities отсутствуют;
- `unavailable` — нет зависимости, устройства или обязательного разрешения;
- `failed` — произошла диагностируемая ошибка;
- `quarantined` — модуль изолирован после повторных сбоев или нарушения policy.

On-demand модуль запускается только для подходящей задачи и выгружается после
настраиваемого периода бездействия. Фоновые модули, например watcher каталога,
работают постоянно только при включённой функции и в заданном бюджете ресурсов.

Отключение модуля:

1. запрещает новые задачи;
2. корректно завершает или отменяет текущие операции;
3. останавливает фоновые процессы;
4. удаляет capabilities из Registry;
5. отзывает временные доступы;
6. сохраняет пользовательские данные, пока пользователь отдельно не запросит их
   удаление.

### 5. Изоляция и взаимодействие

Модули не получают бесконтрольный доступ к памяти core через произвольный
in-process plugin API. Системные и сторонние компоненты по возможности работают
в отдельных процессах и общаются через ограниченные версионированные IPC-
контракты. Компрометация PDF parser или browser adapter не должна автоматически
компрометировать Permission Gateway.

Для раннего MVP допускается запуск доверенных first-party компонентов как Python
packages, если границы интерфейсов уже соблюдаются. Переход к отдельным
процессам не должен менять публичные intent/tool/capability-контракты.

### 6. Ресурсы и профили

Module Manager учитывает класс нагрузки, состояние idle и фоновые задачи. Само
наличие установленного модуля не должно расходовать CPU или RAM, если модуль
выключен или не запущен.

Поставляются настраиваемые профили:

- `Minimal` — core и базовые безопасные системные инструменты;
- `Offline` — локальная модель без сетевых modules;
- `Documents` — каталог, PDF/DOCX и retrieval;
- `Developer` — проекты, Git, процессы, терминал и логи;
- `Full Desktop` — все установленные и явно разрешённые интеграции.

Профиль является набором рекомендуемых состояний, а не отдельной сборкой ОС.
Пользователь может включать и отключать модули индивидуально.

## Первые модули проекта

Уже созданные компоненты становятся первыми first-party modules без немедленного
перемещения файлов:

| Текущий компонент | Будущая capability |
|---|---|
| `services/storage-catalog` | `storage.catalog` |
| `services/indexer` | `documents.index` |
| `ubuntu.system.status.read` | `system.status` |
| локальный model adapter | `model.local` |
| desktop panel | потребитель Registry, не capability-модуль |

Manifest schema и Capability Registry реализованы в `packages/module-sdk` и
`services/capability-registry`. Process Module Manager уже запускает Python-
entrypoint каждого enabled-модуля в отдельном процессе, поднимает обязательные
зависимости, выполняет health check, ограничивает время ответа, карантинит сбойный
startup и выгружает on-demand процессы после idle timeout.

Первыми manifests зарегистрированы `storage.catalog`, `documents.index`,
`documents.pdf`, `storage.watch`, `desktop.applications` и `browser.navigation`.
`storage.watch` является background-модулем: process worker вызывает его lifecycle-
hooks, а bounded scheduler обновляет индекс вне интерактивного запроса. Runtime bridge и
Query Service являются частью core/application layer и используют опубликованные
capabilities, но сами не расширяют полномочия модулей.

## Последствия

- Отключённые и idle-модули не держат тяжёлые зависимости и модели в памяти.
- Пользователь видит, какая возможность установлена, включена и какие права она
  запрашивает.
- Сбои и уязвимости лучше изолированы.
- Функции можно поставлять и обновлять независимо от панели и core.
- Появляются затраты на IPC, manifests, совместимость и управление состояниями.
- Слишком мелкое дробление увеличит задержки и сложность, поэтому модули должны
  соответствовать крупным capability-доменам, а не каждой отдельной функции.

Production IPC core→panel теперь выбран в
[ADR-006](ADR-006-authenticated-unix-runtime-transport.md): Unix socket,
filesystem permissions и Linux `SO_PEERCRED`. IPC отдельных capability-процессов
и дополнительная same-user client binding остаются отдельными решениями.

## Отложенные решения

- формат подписи и канал распространения сторонних модулей;
- transport/sandbox отдельных capability-модулей;
- политика автоматического обновления;
- конкретные CPU/RAM budgets для классов ресурсов;
- публичный SDK и правила совместимости сторонних разработчиков.
