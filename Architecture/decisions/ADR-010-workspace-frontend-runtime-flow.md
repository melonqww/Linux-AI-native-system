# ADR-010: Frontend-поток Workspace Runtime

## Дата

2026-08-21

## Статус

Принято для desktop panel v0.1; backend-контракт не изменяется.

## Контекст

Workspace должен быть единой рабочей областью, а не двумя несвязанными
режимами «чат» и «исполнение». Пользователь может написать обычное сообщение
или сформулировать системную задачу в одной и той же строке. Различие между
разговором и задачей определяет Workspace Runtime, поэтому frontend не должен
пытаться угадывать намерение регулярными выражениями или запускать старые
`compileIntent`/`executePlan` напрямую.

Для задачи пользователю нужно видеть один последовательный ответ: получение
запроса, публичную стадию работы, уточнение или подтверждение, прогресс и
итог. Внутренние рассуждения модели, prompt и traceback в эту ленту не попадают.

## Решение

### Один асинхронный поток

Desktop panel отправляет текст через `POST /v1/workspace/submit` и получает
`run_id`. После этого она периодически читает `POST /v1/workspace/run` и
`POST /v1/workspace/messages` через authenticated Unix IPC. При открытии панели
история и последние запуски восстанавливаются через
`POST /v1/workspace/messages` и `POST /v1/workspace/runs`.

Обычный ответ отображается как разговорное сообщение. Системные уведомления и
`stage_label` отображаются внутри того же Workspace-потока; отдельный старый
этап «компиляция», который выглядел как второй ответ, frontend больше не
создаёт.

### Подтверждение

Для стадии `awaiting_approval` panel показывает локальные кнопки
«Подтвердить»/«Отменить» и вызывает только
`POST /v1/workspace/approval/respond`. После ответа чтение того же `run_id`
продолжается. Ошибка runtime отображается безопасным сообщением и не создаёт
фиктивный результат.

### Task Ledger

Кнопка `Открыть Task Ledger` является маленьким действием под итогом задачи и
появляется только когда связанный run имеет финальную стадию `completed` и
`task_id`. Для `failed` и `cancelled` кнопка намеренно не показывается.

Кнопка не создаёт второй Ledger и не копирует данные. Callback переключает
интерфейс на левую вкладку «Боковая панель», открывает её проекцию Task Ledger
«Последние действия» и сразу запрашивает детали выбранной задачи.

## Последствия

- Обычный диалог и системные задачи используют одну ленту и один жизненный
  цикл run.
- GNOME Shell не блокируется ожиданием модели или capability: frontend только
  опрашивает bounded runtime API.
- Перезапуск панели восстанавливает сообщения и активный run, а завершённая
  задача остаётся доступна через Task Ledger.
- Старые frontend-вызовы `compileIntent` и `executePlan` сохранены в клиенте
  для совместимости с другими экранами, но Workspace их больше не использует.
- Переход использует уже существующий экран Ledger внутри «Боковой панели» и
  не плодит дубликаты.
