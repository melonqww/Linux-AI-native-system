# ADR-030: Явное различение смысла content-поиска

**Статус:** принято 2026-09-11

## Контекст

Capability `documents.query.search` передавала один параметр `text` для двух
разных пользовательских намерений: поиска документов по теме и поиска
документов с конкретной фразой. При этом semantic retriever и лексический
индекс имели разные свойства, но контракт не позволял отличить их выбор.

Из-за этого следующий этап поиска не мог безопасно решить, допустимы ли
семантически похожие результаты. Нельзя прятать такое решение в ядре или
выводить его из набора случайных слов: это часть смысла операции, который
должен быть виден плану и модулю.

## Решение

В `documents.query.search` добавляется необязательный для metadata-only и
обязательный для непустого `text` параметр `content_match`:

- `semantic` — пользователь ищет тему или смысл;
- `exact_phrase` — пользователь указывает фразу, которая должна быть найдена.

Intent Validator отклоняет content-запрос без этого выбора и не принимает
`content_match` для metadata-only запроса. Query Runtime применяет ту же проверку
на границе JSON API. `DocumentQuery` переносит значение типизированным enum.
Выбор объясняется только module-owned описанием операции и её аргументов; общий
prompt Intent Compiler не содержит имени `search_documents` или значений этого
конкретного контракта.

Условная обязательность описывается module-owned ключом `coRequiredWith`:
`content_match` требуется вместе с `text`, но не для metadata-only запроса.
Intent Compiler проверяет такой контракт универсально и удаляет служебный ключ
из стандартной JSON Schema, передаваемой модели. Если малая модель пропустила
производный enum, ограниченный повторный review может восстановить только
значение из разрешённого enum и только при валидном аргументе-триггере текущего
запроса. Свободные строки, пути и имена эта поблажка не затрагивает.
Для устойчивости малой локальной модели модуль также объявляет `reviewChoices`:
группы коротких смысловых ярлыков для каждого enum и для `$misplaced`. Проверка
одного условного аргумента идёт отдельным узким model-вызовом. Ядро принимает
только объявленный ярлык; `$misplaced` может убрать лишь необязательный аргумент,
значение которого буквально присутствует в текущем сообщении. Так имя папки или
тип файла не превращаются в тему документа, но произвольное значение не может
быть удалено или добавлено.

Проверка применяется и к уже заполненному основной моделью условному enum.
Иначе модель могла бы обойти границу ролей, одновременно записав тип файла в
`text` и самостоятельно выбрав `content_match`. Узкий review остаётся
авторитетным только в пределах закрытых module-owned ярлыков: он может исправить
enum либо удалить необязательный, буквально присутствующий trigger вместе с
зависимым значением; другие аргументы и операции он менять не может.

Малая модель также может поместить пользовательскую тему в зависимый enum,
например передать `content_match: "математика"` вместо `text: "математика"`.
Перед review Intent Compiler универсально сверяет такие значения с
`coRequiredWith`. Перенос в связанный аргумент разрешён только если исходное
значение невалидно на текущем месте, буквально присутствует в текущем сообщении,
валидно ровно для одного ещё не заполненного связанного аргумента и после
переноса весь обычный контракт продолжает проверяться. Неподтверждённое или
неоднозначное значение приводит к уточнению. Это исправляет перепутанную роль,
не добавляя в ядро словари тем, языковые шаблоны или имена операций.

Если модель одновременно сохранила валидный связанный аргумент и продублировала
его значение в зависимом enum, значение не переносится поверх уже заполненного
поля. Intent Compiler удаляет только невалидный enum и отдаёт валидный,
буквально подтверждённый trigger тому же module-owned review. Такой ремонт
разрешён лишь для необязательного dependent с `reviewChoices`, ровно одним
валидным заполненным peer и grounding обоих значений в текущем сообщении.
Review заново выбирает разрешённый enum; ошибка review или любая неоднозначность
по-прежнему приводит к уточнению, а не к выполнению операции.

Review различает тему и точную фразу по требованию пользователя, а не по тому,
что слова буквально встречаются в запросе. `exact_phrase` допустим только когда
пользователь явно требует дословного вхождения; обычный запрос «документы по
теме» остаётся `semantic`, а «мои документы» само по себе не считается темой
содержимого.

`extensions` остаётся явным структурным полем каждого поискового вызова: пустой
массив означает отсутствие фильтра, а названный пользователем тип файла должен
быть нормализован в суффикс. Это не позволяет малой модели молча потерять
ограничение вроде PDF.

Нейтральное отсутствие ограничения объявлено самим модулем как runtime-default
`extensions: []`. Общий каталог проверяет тип default при загрузке контракта,
не передаёт его модели как источник истины и применяет перед строгой валидацией.
На текущей границе разрешён только нейтральный default пустого массива: модуль
не может таким механизмом подставить путь, объект или непустой фильтр, которого
не называл пользователь.
Тот же общий этап считает пустую необязательную строку отсутствующим аргументом;
если вместе с ней модель прислала необязательный зависимый аргумент
`coRequiredWith`, зависимый аргумент также удаляется. Если trigger вообще не был
прислан, зависимое значение не исправляется молча и план отклоняется — это
сохраняет fail-closed поведение при реально потерянном пользовательском смысле.

Query Service исполняет выбор различными путями. `semantic` сохраняет гибридный
поиск: лексические совпадения дополняются близкими по смыслу фрагментами локального
retriever. `exact_phrase` строит одну экранированную FTS-фразу из токенов запроса;
они должны встретиться подряд и в исходном порядке. В этом режиме semantic
retriever не вызывается, поэтому семантическая близость сама по себе никогда не
считается доказательством наличия фразы.

## Последствия

- План явно сообщает, что именно пользователь имел в виду под поиском текста.
- Модули и ядро больше не должны угадывать режим по одному полю `text`.
- Новые условные связи аргументов объявляются модулем через общий контракт, без
  добавления имени операции в prompt или validator ядра.
- Перепутанное моделью положение подтверждённого значения исправляется по
  связям схемы; произвольное значение не переносится и не исполняется.
- Старые прямые вызовы `DocumentQuery` должны указать `content_match` для
  content/hybrid запросов; metadata-запросы не получают это поле.
- `exact_phrase` не получает semantic-only результаты и не передаёт содержимое
  embedding-provider; его выдача подтверждена локальным FTS.
- Фразовое совпадение определяется токенизатором Unicode FTS: регистр и знаки
  пунктуации несущественны, но порядок и соседство слов обязательны.
- Лаборатория содержит парные end-to-end сценарии на общей двухфайловой
  фикстуре. Она независимо проверяет выбранный `content_match` в сохранённом
  плане и точный набор путей backend-выдачи. Поэтому правильный ответ модели при
  неверном алгоритме — и правильная выдача при неверном плане — не дают зелёный
  результат.
- Версия `documents.query` повышена до `0.6.1`: `0.5.0` добавила обязательный
  выбор, `0.6.0` начала реально применять его к алгоритму выдачи, а `0.6.1`
  расширила module-owned intent examples для явного повторного поиска без
  словаря фраз в Workspace.

ADR-030 дополняет ADR-023, ADR-025, ADR-026 и ADR-029.

Уточнение от 2026-09-24: Query Service помечает поля `text`, `name_terms` и
`extensions` общими `semanticRole` в контракте модуля. Валидатор не передаёт
эти служебные метки модели. Если модель поместила явно названное имя файла
в предикат содержимого, общий этап по ролям переводит только это буквальное
имя в поиск по метаданным. Явная просьба найти фразу внутри файла остаётся
поиском по содержимому. Это не словарь названий файлов и не угадывание темы.
