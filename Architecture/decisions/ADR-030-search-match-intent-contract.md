# ADR-030: Явное различение смысла content-поиска

**Статус:** принято 2026-09-11

## Контекст

Capability `documents.query.search` передавала один параметр `text` для двух
разных пользовательских намерений: поиска документов по теме и поиска
документов с конкретной фразой. При этом semantic retriever и лексический
индекс имели разные свойства, но контракт не позволял отличить их выбор.

Из-за этого следующий этап поиска не мог безопасно решить, допустимы ли
семантически похожие результаты. Нельзя прятать такое решение в ядре или
выводить его из набора случайных слов: это часть смысла операции, который
должен быть виден плану и модулю.

## Решение

В `documents.query.search` добавляется необязательный для metadata-only и
обязательный для непустого `text` параметр `content_match`:

- `semantic` — пользователь ищет тему или смысл;
- `exact_phrase` — пользователь указывает фразу, которая должна быть найдена.

Intent Validator отклоняет content-запрос без этого выбора и не принимает
`content_match` для metadata-only запроса. Query Runtime применяет ту же проверку
на границе JSON API. `DocumentQuery` переносит значение типизированным enum.
Выбор объясняется только module-owned описанием операции и её аргументов; общий
prompt Intent Compiler не содержит имени `search_documents` или значений этого
конкретного контракта.

Условная обязательность описывается module-owned ключом `coRequiredWith`:
`content_match` требуется вместе с `text`, но не для metadata-only запроса.
Intent Compiler проверяет такой контракт универсально и удаляет служебный ключ
из стандартной JSON Schema, передаваемой модели. Если малая модель пропустила
производный enum, ограниченный повторный review может восстановить только
значение из разрешённого enum и только при валидном аргументе-триггере текущего
запроса. Свободные строки, пути и имена эта поблажка не затрагивает.
Для устойчивости малой локальной модели модуль также объявляет `reviewChoices`:
группы коротких смысловых ярлыков для каждого enum и для `$misplaced`. Проверка
одного условного аргумента идёт отдельным узким model-вызовом. Ядро принимает
только объявленный ярлык; `$misplaced` может убрать лишь необязательный аргумент,
значение которого буквально присутствует в текущем сообщении. Так имя папки или
тип файла не превращаются в тему документа, но произвольное значение не может
быть удалено или добавлено.

`extensions` остаётся явным структурным полем каждого поискового вызова: пустой
массив означает отсутствие фильтра, а названный пользователем тип файла должен
быть нормализован в суффикс. Это не позволяет малой модели молча потерять
ограничение вроде PDF.

На этом этапе меняется только контракт и прохождение намерения. Реальное
разделение алгоритмов, фразовый FTS и запрет semantic hits для
`exact_phrase` относятся к следующему этапу и намеренно не включены в это
изменение.

## Последствия

- План явно сообщает, что именно пользователь имел в виду под поиском текста.
- Модули и ядро больше не должны угадывать режим по одному полю `text`.
- Новые условные связи аргументов объявляются модулем через общий контракт, без
  добавления имени операции в prompt или validator ядра.
- Старые прямые вызовы `DocumentQuery` должны указать `content_match` для
  content/hybrid запросов; metadata-запросы не получают это поле.
- До реализации алгоритмического разделения `content_match` не меняет состав
  выдачи. Это осознанная промежуточная граница между пунктами 2 и 3.
- Лабораторные сценарии и их оракулы в ADR-030 не меняются.
- Версия `documents.query` повышается до `0.5.0`, поскольку прежний content-вызов
  без `content_match` теперь отклоняется.

ADR-030 дополняет ADR-023, ADR-025, ADR-026 и ADR-029.
