# ADR-012: Ollama как user-local provider-модуль

## Статус

Принято и реализовано.

## Контекст

`model.ollama` управляет весами моделей, но не должен устанавливать inference
runtime. Официальная системная установка Ollama меняет `/usr`, создаёт service
и требует root. Передача этих полномочий runtime расширила бы доверенную базу и
засорила модельный модуль deployment-логикой.

## Решение

Создан отдельный `provider.ollama`. Он обнаруживает внешнюю Ollama либо после
явного решения пользователя устанавливает официальный архив в user-local
каталог AI-native Linux. Модуль:

- не использует root, shell и vendor installer script;
- поддерживает Linux amd64 и arm64;
- получает release metadata только из официального GitHub API;
- требует SHA-256 asset digest и ограничивает размер загрузки;
- безопасно распаковывает только `bin/` и `lib/`;
- публикует бинарник атомарным переключением `current`;
- хранит `install/later/never` в собственной SQLite-базе.

Module Manager добавляет управляемый `current/bin` в `PATH` изолированных
workers. `provider.ollama` является единственным владельцем процесса для этой
user-local копии. `model.ollama` зависит от provider и работает только через
loopback API: он больше не ищет бинарник и не запускает `ollama serve`.

Внешняя системная Ollama по-прежнему имеет приоритет, если её API уже доступен.
Если найден только системный бинарник, но service не работает, provider сообщает
`external_server_unavailable`, не запуская бинарник от имени desktop-пользователя.
Так системное и user-local хранилища моделей не подменяют друг друга.

## Последствия

- установка не требует административного подтверждения ОС;
- повреждённый или подменённый архив не публикуется;
- CUDA/ROCm и системные services остаются вне текущего scope;
- внешний системный Ollama продолжает иметь приоритет;
- обновление provider можно добавить тем же проверенным lifecycle-контрактом.
