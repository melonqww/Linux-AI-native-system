# ADR-016: Подключение менеджера приложений к runtime и GNOME-панели

## Статус

Принято и реализовано для Snapd v0.3.

## Контекст

ADR-015 определил долговечные задачи установки приложений, но модуль оставался
автономным. Панели требовались каталог, библиотека, прогресс, пауза, удаление и
бэкапы. При этом прямой вызов snapd из GNOME-интерфейса обошёл бы ядро,
Permission Gateway и подтверждения пользователя. Ошибка нового модуля также не
должна ломать панель, плагины или существующий поиск файлов.

Дополнительные сложности:

- выключение ПК или потеря сети не должны уничтожать задачу;
- успешный запрос к snapd ещё не означает завершённую установку;
- удаление без бэкапа требует более сильного подтверждения;
- частое обновление процентов не должно заново проигрывать анимации интерфейса;
- второй экземпляр runtime не должен одновременно восстанавливать те же задачи.

## Решение

`software.manager` зарегистрирован как отдельный background capability-модуль.
Он хранит задачи и бэкапы в собственной SQLite-базе, а привилегированную операцию
оставляет snapd и штатному Polkit. Ядро и панель не передают произвольные package
IDs: приложение выбирается только из встроенного каталога из 20 разрешённых Snap
пакетов.

Runtime публикует единый snapshot каталога, задач и бэкапов, а изменяющие
операции разделены на серверные стадии:

- `prepare` создаёт долговечную задачу без изменения системы;
- `commit` выполняется только после подтверждения через защищённый Unix IPC;
- удаление проходит второе финальное подтверждение;
- `pause`, `resume` и `cancel` принимают только существующий `task_id`.

Восстановление бэкапа является отдельной подтверждаемой commit-операцией. Так
как snapshot Snap содержит данные, но не пакет приложения, координатор сначала
создаёт обычную долговечную задачу установки. Только после её успешного
завершения запускается `snap restore`; обе стадии сохраняются в SQLite и
продолжаются после перезапуска runtime.

Permission Gateway проверяет risk, transport и scope `software.manage`. Worker
повторно сверяет тип действия и текущую confirmation-stage с сохранённой задачей,
поэтому UI не может подменить установку удалением или пропустить подтверждение.
Loopback HTTP не получает software endpoints.

Recovery worker запускается только после того, как основной runtime успешно
занял единственный Unix socket. После перезапуска он сверяет сохранённый change ID
со snapd. При отсутствии сети загрузка ждёт подключения и продолжается
автоматически; ручная пауза остаётся ручной. Завершение установки отправляется в
системный центр уведомлений Linux, а не рисуется внутри панели.

GNOME-панель показывает верхние разделы «Каталог» и «Библиотека»; внутри
библиотеки находятся «Установленные» и «Бэкапы». Она выводит локальные иконки,
источник и параметры перед установкой, галочку сохранения бэкапа перед удалением,
процент, скорость и ETA. Snapshot опрашивается периодически, но дерево акторов
обновляется только при изменении данных. Анимация применяется к открытию экрана и
подтверждениям, а не к каждому новому проценту. Viewport панели явно обрезает
отрисовку по своей области, чтобы прокрутка не оставляла старые строки за правой
или нижней границей. Недоступность модуля локализуется внутри раздела приложений;
остальные возможности панели продолжают работать.

GNOME получает обнаруженные snapd `.desktop` IDs, а состояние запуска проверяет
через `Shell.AppSystem`. Принятый вызов `activate()` показывает «Запускается», но
«Запущено» появляется только после состояния `Shell.AppState.RUNNING`. Закрытие
выполняется мягким `request_quit()`. Выбранная при установке опция закрепления
добавляет подтверждённый desktop ID в избранное GNOME.

## Последствия

- установка переживает закрытие панели, потерю сети и перезапуск системы;
- GNOME UI не получает прямого доступа к snapd или shell;
- пользователь видит реальное состояние долговечной задачи и управляет ею;
- удаление без бэкапа нельзя выполнить случайным одиночным нажатием;
- модуль можно расширить адаптерами Flatpak и APT без изменения основного UI;
- файловый поиск, индексатор и PDF-модуль не зависят от менеджера приложений;
- реальные Snapd, Polkit, NetworkManager и GNOME Shell всё ещё требуют проверки
  непосредственно на Ubuntu.
