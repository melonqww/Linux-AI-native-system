# ADR-009: Единая системная рабочая область

## Статус

Принято как фундамент Workspace Runtime v1.

## Контекст

Центральная поверхность — не ChatGPT-клон и не список независимых диалогов.
Пользователь работает с одной системой: иногда общается с локальной моделью,
иногда просит найти, открыть, скопировать или обработать системные объекты.
Обычное «привет» не должно превращаться в execution plan, а команда не должна
исполняться как свободный текст модели.

Видимые сообщения нужны недолго, факты о системной работе — дольше, а доверенный
контекст «их/туда» должен переживать рестарт. Это разные данные с разными
границами доверия и retention.

## Решение

### Одна рабочая лента

Workspace не имеет conversation/thread списка. `workspace-service` хранит одну
локальную ленту сообщений не более 24 часов. Сообщения пользователя, ответы,
уточнения и краткие итоги имеют UUID, тип и optional `task_id`. Автоматическая
очистка не затрагивает Task Ledger и доверенную task-memory.

### Три независимых срока жизни

1. Workspace messages и завершённые workspace runs — 24 часа.
2. Task Ledger — 7 суток и только факты операций, ссылки и состояния.
3. Operational task-memory — активная коллекция и последняя destination до
   замены, очистки или недоступности объекта; она хранится в отдельной SQLite.

Будущая semantic memory предпочтений не создаётся из каждого сообщения
автоматически. Она потребует отдельной policy, provenance и пользовательского
управления удалением.

### Маршрутизация моделью, полномочия системой

Workspace Model Router предоставляет Qwen закрытый выбор:

- вернуть обычный bounded assistant response без tool calls;
- вызвать одну или несколько известных semantic tools для системной команды.

Прямой текст означает только общение и не имеет системных полномочий. Tool calls
повторно проходят существующие Intent Validator, Planner, Permission Gateway и
Orchestrator. Regex-список приветствий и захардкоженные пользовательские команды
не используются. Если выбор неоднозначен, система задаёт уточнение и ничего не
исполняет.

### Публичные стадии вместо chain-of-thought

Каждое обращение получает `run_id` и проходит закрытый автомат:

```text
received → understanding → planning → executing
                                  ↘ awaiting_approval ↗
                     → summarizing → completed
```

Фронтенд получает stage, локализованную короткую подпись, `started_at`, точное
`elapsed_ms` и `stage_elapsed_ms`. Model reasoning, prompt, traceback и скрытые
шаги не сохраняются и не передаются. ETA в v1 отсутствует: система не показывает
выдуманный прогноз. Позже его можно вычислять только по статистике одинаковых
capability-задач.

Для обычного общения путь короче:
`received → understanding → summarizing → completed`.

### Фактический итог

После системной операции итоговый ответ строится только из redacted
OrchestrationResult и Task Ledger projection. Qwen может сделать формулировку
естественной, но не получает права добавлять пути, количества или утверждения,
которых нет в результате. Невалидный model summary заменяется детерминированным
системным итогом. Workspace run связывается с `task_id`; после удаления суточного
сообщения задача остаётся доступна в Task Ledger.

### Асинхронный API

`POST /v1/workspace/submit` должен быстро вернуть `run_id`, после чего frontend
читает bounded status/messages через authenticated Unix IPC. Выполнение модели и
capabilities не блокирует GNOME Shell. Approval остаётся отдельным подтверждением
существующего Orchestrator, а не согласием «на всё» внутри workspace.

## Последствия

- Рабочая область остаётся системной, а не мессенджером.
- Перезапуск не ломает ссылки «их/туда».
- Очистка сообщений через сутки не стирает историю реальных действий.
- Qwen отвечает на приветствие и использует semantic tools для команд, но не
  определяет permissions и не сообщает неподтверждённые результаты.
- Streaming и статистический ETA являются следующими совместимыми расширениями,
  а не частью первого фундамента.
